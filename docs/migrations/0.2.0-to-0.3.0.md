# Migration: 0.2.0 → 0.3.0

## Purpose

Version 0.3.0 adds the research flow, two anchors, and parameterized reporting standards. It is a builder-level workflow change. It does **not** mean an existing research project must change its approved design, its research questions, or its collected evidence.

## What changed

- `GRO.md` — the Grand Research Outline — and its [rules](../gro.md): eleven numbered sections following the research outline, each a paragraph stating where that part is going and why, verified by the researcher.
- `brain.md` and the [data structure](../data-structure.md): typed statements with links, plus `DAT`, `PRM`, and `RUN` records.
- The nine-stage [research flow](../research-workflow.md) and the flow gates FG0–FG4 that bundle G0–G7 into hard stops.
- Three literature tracks with separate folders, presets, and default windows.
- `parameters/` with search and reporting presets; a reporting standard is now a parameter selected by the design.
- [Writing standards](../writing-standards.md) and the [methodology sources register](../methodology-sources.md).
- Nine new templates and revisions to all fourteen existing ones.
- Validator checks for dangling identifiers and GRO entry discipline; `scripts/coherence_report.py`.

## Migration procedure for a RESEARCH project

1. Create a migration Issue.
2. Copy `GRO.md`, `brain.md`, `parameters/`, and the new folders from the 0.3.0 builder. Set the project name and RESEARCH mode in both anchors.
3. **Backfill the anchors from what already exists, not from memory.** Register the statements the project has actually made as typed statements in `brain.md`, citing the source notes, data, and decisions that already support them. Leave a statement `UNKNOWN` rather than inventing an upstream link.
4. Fill the `GRO.md` sections the project has already passed, each reporting the direction that part actually took and the reasoning behind it, and mark them `REPORTED` for the researcher to verify. Sections not yet reached stay `NOT YET REACHED`. Do not fabricate a revision history for decisions whose reasoning cannot be reconstructed; record it as unknown.
5. Register the parameters already in use — search windows, screening criteria, sampling logic, analysis thresholds — as `PRM` records with their existing justifications. A parameter whose justification cannot be reconstructed is recorded as `UNKNOWN`, not invented.
6. Select the reporting standard the design requires and register it as a `PRM` of type `reporting` from the presets.
7. Map the existing literature to the three tracks. Sources already collected do not need to be re-searched; record which track each belongs to.
8. Run `python scripts/validate_repository.py` and `python scripts/coherence_report.py`, and resolve dangling identifiers.
9. Update the pinned builder version only after the migration PR is reviewed and merged.

## What should not be migrated automatically

Do not change research questions, approved designs, instruments, samples, collected data, ethics procedures, or manuscript claims to fit the new structure. If an existing artifact conflicts with a flow gate — for example a manuscript drafted before every research question was answered — record the conflict and reopen the affected gate rather than silently restructuring the work.

Backfilling the anchors is a recording exercise. It must not become a retrospective rewrite that makes the project look as though it always followed this flow.

## Verification

A migration is mechanically complete when `GRO.md` and `brain.md` exist and are synchronized, the parameter sets in use are registered, the reporting standard is selected, the validator passes, and the coherence report shows no dangling identifiers.

Mechanical completion is not proof that the research direction is sound. That is what the researcher confirms in `GRO.md`.
